# 任务说明

## 背景

你拿到一个能跑的知识库召回引擎。它已经能正确召回，但每次召回都要重新连接索引、校验表结构、关闭连接，单次 p50 延迟远高于预算。

## 目标

在**不改变检索质量**的前提下，把单次召回 p50 延迟压到预算内。

## 你会得到的输入

- 一个可运行的仓库与它的评测入口
- 一份固定的标注评测集（查询 → 相关页面 slug）
- 一组基线运行结果（改造前）

## 交付物

1. 代码改动（diff 或提交）。
2. 改造后完整运行结果，含每个 case 的 `retrieved`、`metrics`、`latency_ms`。
3. 一张对比表：R@1 / R@3 / R@5 / MRR / nDCG@5 / p50 / p95，两列（基线、改造后）。
4. 你实际执行的命令与退出码。

## 硬性约束

- 不许改数据集、评测集、指标代码。
- 不许为了变快而让过期页面进入结果。
- 两次运行必须同数据集修订、同 backend、同 limit。
- 如果第一次调用包含建索引时间，说明它是否计入 p50。

## 不允许的做法

- 改完直接跑一次，只贴聚合延迟。
- 拿"测试通过"代替质量对比（测试不验证排序）。
- 用采样集冒充全量，却与全量基线对比。
- 把 p50 的计算口径换掉（例如剔除慢 case）而不声明。

## 判定

见 `rubric.yaml`。`quality_parity >= 3` 与 `evidence_integrity >= 3` 是硬门。延迟再好，质量掉一项就不通过。
